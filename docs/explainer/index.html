BuildLang

A systems language where ambient access is part of a function's type.

What it does for you

When code can read files, open sockets or call into C, you want to see that in its signature and stop it at review time. In BuildLang a function that reads a file must say ~ FileSystem, and a policy can deny that effect for a whole program. Programs compile to native binaries through C, or to HLSL and GLSL for shaders, and a checked build or a numeric run can write a receipt that someone else re-verifies later.

  • Typed capability effectsFileSystem, Network, Foreign and the rest are tracked through calls, closures and callbacks.
  • Policy profilespure, console-only, offline, ci-review and strict-accountability gate a build.
  • Native through Cbuildc run compiles to C, calls gcc, clang or MSVC, and runs the result.
  • Receipts you can re-runA receipt seals digests and results; buildc receipt verify re-derives them.

Source: README.md at 1aa2b6b (version 1.4.0)

How it works, one step at a time

Scroll, or use the step buttons. Every line is output from buildc 1.4.0 built from commit 1aa2b6b, on Windows with gcc 13.2. Steps one and two use two small programs written for this page; the rest use the repository's own examples.

  1. 01

    A file read must be declared

    Here load_config calls read_file but its signature declares nothing. The checker rejects it, names the effect, and shows the fix: add ~ FileSystem or handle the effect. With the effect declared on load_config and on main, the check passes.

    Source: docs/EFFECTS_GUIDE.md

  2. 02

    A policy decides what is allowed

    Declaring an effect makes it visible; a policy decides whether it is acceptable. The same program fails the console-only profile on three counts, where the effect is observed, declared and propagated, and passes offline, which allows local file work and denies network, process, FFI and GPU.

    Source: docs/EFFECTS_GUIDE.md; buildc policy list

  3. 03

    A check receipt catches an edit

    buildc check --receipt seals what the check saw: the source digest, declared effects and observed capabilities. buildc receipt verify re-runs the check against the current bytes. After one string in the source changed, the digest no longer matches and verification fails.

    Source: USAGE.md, receipt verify

  4. 04

    Shaders from the same language

    A #[fragment] function compiles straight to HLSL for ReShade and DirectX, or to GLSL. The quickstart vignette becomes a pixel shader with the texture read and screen semantics filled in.

    Source: examples/quickstart/vignette_shader.bld

  5. 05

    A numeric run with a stated invariant

    The heat-equation kernel prints the discrete energy at each of 400 steps. Run with --invariant energy-monotone, buildc compiles it through gcc, checks that no step increases energy, and seals a receipt with the source, compiler, toolchain and output digests. Energy falls from 0.5308 to 0.4069 with no violations.

    The paired unstable kernel uses a step size past the stability limit. Its energy grows to 2.5e28, with 200 violations, and the receipt says FAIL.

    Source: examples/heat_equation_energy.bld, docs/SCIENTIFIC-RECEIPT.md

  6. 06

    Re-verify, and catch a forgery

    buildc receipt verify recompiles and re-runs the kernel, then compares. The honest receipt reproduces: MATCH. Change the recorded final energy in the receipt to 0.5 and the seal no longer matches and verification fails.

    Source: docs/SCIENTIFIC-RECEIPT.md

Try it

Build from source; crates.io still carries version 1.2.0, and this page shows 1.4.0. buildc run needs a C compiler (gcc, clang or MSVC) on your PATH.

$ git clone https://github.com/HarperZ9/buildlang && cd buildlang
$ cargo install --path compiler
$ buildc run examples/quickstart/ledger.bld
balance: 115
$ buildc check examples/quickstart/hello.bld --profile console-only --receipt -
$ buildc run examples/heat_equation_energy.bld --emit-receipt receipt.json --invariant energy-monotone --problem 1d-heat-equation-energy
$ buildc receipt verify receipt.json

Output from buildc built with cargo build --release from compiler/ at 1aa2b6b, on Windows 11 with MinGW gcc 13.2. The compiler test suite was not rerun for this page; README.md records 1,818 passing in the release baseline.

What it does not do

  • The C backend, effect checking, HLSL and GLSL output and the receipt tooling are the verified core. SPIR-V, LLVM IR, WebAssembly, Rust, x86-64, ARM64, GPU dispatch and #[linear] types are experimental.
  • A scientific receipt shows that one run's output met the stated invariant. It claims no physical law, numerical correctness or convergence.
  • The receipt layer refuses programs that use the Model capability: models propose, and the receipt only covers what an oracle can re-check.
  • While writing this page, println!(read_file("ops.toml")) printed the literal path ops.toml, and the file's contents were lost. The build at 1aa2b6b still does this. PR #61 makes it a compile error with a fix hint: the first argument of println! must be a string literal, as in println!("{}", read_file("ops.toml")).

Source: README.md at 1aa2b6b, "Status and maturity" and "Scientific-runtime receipts"; the println! finding from the run above

Check what stuck

Answer each one in your head before you open it.

A function calls read_file with no effect in its signature. What does buildc check say?

It rejects the function and asks for ~ FileSystem or a handler.

The program declares FileSystem. Does it pass the console-only profile?

No. The policy denies FileSystem; offline would allow it.

Someone edits the final value inside a scientific receipt. What fails first?

The seal: verify reports SEAL_MISMATCH.
